# Сценарій KITTI

`KittiScenario()` у `include/sensor_fusion/io/kitti/kitti_scenario.h` перетворює поїздку, яку прочитала `ReadKittiOxts()`, на ряди `imu` і `reference` для [`Scenario`](ekf-scenario.md). Функція повторює `load_scenario()` з `foreign_impl/ref_ekf.py`, тож C++ фільтр і еталон на filterpy стартують з однакових чисел. Фікси GNSS приходять з CSV-файлу, який пише Python; див. `include/sensor_fusion/io/gnss/gnss_csv.h`.

## Що в кожному ряді

| Поле | Звідки |
| --- | --- |
| `imu[i]` | `t`, `ax`, `wz` запису `i`, пара осей тіла з [розвідки KITTI](kitti-oxts-survey.md#дві-системи-осей) |
| `reference[i].state.east` | `R * cos(lat0) * (lon - lon0)` |
| `reference[i].state.north` | `R * (lat - lat0)` |
| `reference[i].state.yaw` | `yaw` з OXTS, розгорнутий як у `numpy.unwrap()` |
| `reference[i].state.v` | `vf` з OXTS, швидкість уперед уздовж землі |

`R` — 6 378 137 м, екваторіальний радіус WGS-84. Кути в радіанах. Запис 0 — початок координат, тож `reference[0]` лежить у `(0, 0)`, а його `yaw` і `v` — початковий стан обох фільтрів.

East і north рахуються на пласкій землі навколо першого запису. На поїздці в кілька сотень метрів похибка такого наближення значно менша за шум GNSS. Воно лишається, бо його використовує еталон, а не тому, що це найкраща проєкція.

## Збіг із numpy біт у біт

Кожен вираз повторює Python операція за операцією. На поїздці 0009 усі 447 рядків `t`, `east`, `north`, `yaw`, `v`, `ax` і `wz` побітово збігаються з `load_scenario()`; перевірено з numpy 2.2.6.

Порядок операцій важливий. `numpy.radians(x)` — це `x * (pi / 180)`, де `pi / 180` — одна стала. `x * pi / 180` округлює двічі й дає інший `double`:

| Формула | Збігається з `numpy.radians` | Побітово однакових рядків на 0009 | Найбільша різниця |
| --- | --- | --- | --- |
| `x * (pi / 180)` | завжди | 447/447 east, 447/447 north | 0 |
| `x * pi / 180` | 72% випадкових кутів; 277/447 широт, 377/447 довгот | 86/447 east, 47/447 north | 1.2e-10 м east, 1.4e-9 м north |

Різниця значно менша за міліметр, тож траєкторія не змінюється. Але побітове порівняння з filterpy вона ламає, а наступний крок може її збільшити. `internal::Radians()` використовує першу форму.

Так само уважно зроблено решту:

- `east` спершу множить `R * cos(lat0)`, а потім на `(lon - lon0)`, бо Python обчислює `EARTH_RADIUS_M * np.cos(lat[0]) * (lon - lon[0])` зліва направо.
- `internal::Unwrap()` повторює `numpy.unwrap()`: обгорнутий стрибок — це `mod(jump + pi, 2 pi) - pi` з правилом знака `numpy.mod()`, стрибок рівно `+pi` лишається `+pi`, а поправки сумуються по черзі, як у `cumsum`.
- Час — це `(ns - ns0) * 1e-9`, той самий добуток в обох мовах.
- Усі широти й довготи спершу переводяться в радіани й зберігаються, а віднімання йде потім, так само як numpy спершу створює масиви `np.radians(...)`. gcc на `-O2` і вище зливає множення і наступне додавання чи віднімання в одну операцію з одним округленням, навіть із `-std=c++20`. Злите `Radians(lon) - lon0` округлюється один раз замість двох: запис 0 опиняється приблизно за 1e-11 м від початку координат, а не в ньому, і жоден рядок не збігається з numpy. Збережене значення з пізнішим відніманням злити не можна.

`cos` береться з математичної бібліотеки C++ і з numpy, які на іншій платформі можуть розійтися в останньому біті. На цій машині вони збігаються.

## Запуск порівняння

`apps/report/kitti_run.cpp` проганяє C++ фільтр на поїздці двічі: з усіма фіксами GNSS і з вирізаним відключенням. Обидві траєкторії він записує для `ref_ekf.py --own`. Фікси приходять із Python, бо генератор випадкових чисел numpy в C++ не повторити. Спершу запустіть еталон, який запише файли GNSS:

```bash
python foreign_impl/ref_ekf.py data/kitti/2011_09_26/2011_09_26_drive_0009_sync/oxts --out build/report/kitti
```

Потім C++ фільтр і знову еталон, щоб порівняти їх:

```bash
cmake --build build --target kitti_run
build/kitti_run --oxts data/kitti/2011_09_26/2011_09_26_drive_0009_sync/oxts \
    --gnss build/report/kitti/gnss_full.csv \
    --gnss-outage build/report/kitti/gnss_outage.csv
python foreign_impl/ref_ekf.py data/kitti/2011_09_26/2011_09_26_drive_0009_sync/oxts \
    --out build/report/kitti \
    --own build/report/kitti/kitti_estimates.csv \
    --own-outage build/report/kitti/kitti_estimates_outage.csv
```

Беріть файли GNSS, які пише нинішній `ref_ekf.py`. Файли від старішої версії містять інші фікси, і тоді фільтри розходяться на метри.

| Прапорець | Типово | Значення |
| --- | --- | --- |
| `--oxts DIR` | обов'язковий | каталог oxts з KITTI |
| `--gnss FILE` | обов'язковий | фікси на всю поїздку, `t,east,north` |
| `--gnss-outage FILE` | обов'язковий | ті самі фікси з вирізаним вікном відключення: кожен фікс `--gnss` поза вікном, у тому самому порядку, і жодного всередині |
| `--out DIR` | `build/report/kitti` | каталог для результатів, створюється за потреби |
| `--outage-start S`, `--outage-length S` | 15, 15 | вікно відключення `[start, start + length)` для метрик; має бути тим вікном, яке `ref_ekf.py` вирізав із фіксів |
| `--initial-position-std`, `--initial-yaw-std`, `--initial-speed-std`, `--accel-noise-density`, `--gyro-noise-density`, `--gnss-position-std` | `EkfConfig` | параметри фільтра, назви як у полів `EkfConfig` |

Фільтр стартує з `reference[0]`, як і `ref_ekf.py`. Типові значення `EkfConfig` дорівнюють `PARAMS` у `ref_ekf.py`. Передавайте прапорець, лише якщо те саме значення змінено й у Python.

Результати, по рядку на крок IMU:

- `kitti_estimates.csv` і `kitti_estimates_outage.csv`, стовпці `t,east,north,yaw,v,std_east,std_north,updated`;
- кожне число записано найкоротшим текстом, що читається назад у той самий `double`, тож два запуски дають однакові файли;
- `updated` дорівнює 1 на кроці, який використав фікс;
- `kitti_metrics.json` містить показники точності з [метрик](metrics.md): RMSE сирого GNSS і фільтра, RMSE у вікні відключення з GNSS до нього і без, та відношення похибок на моменті повторного захоплення.

Кожен файл спершу пишеться як `<назва>.tmp` і перейменовується, коли всі три готові, тож невдалий запуск лишає попередні результати як були.

stdout лишається порожнім. Короткий статус або причина збою йде в stderr. Код виходу:

- 0: готово;
- 1: вхідний файл не читається, файл відключення не є повним файлом без вікна відключення, фільтр зазнав збою або результат не записати;
- 2: погані аргументи, зокрема параметри фільтра, які відкидає `EkfConfig`.

На поїздці 0009 обидві C++ траєкторії збігаються з filterpy 2.0.0 до 8e-14 м за положенням і до 2e-14 м за стандартним відхиленням, і через clang, і через gcc (див. [метрики](metrics.md#збіг-із-ref_ekfpy)). Метрики:

| Метрика | Значення |
| --- | --- |
| RMSE сирого GNSS | 2.108 м |
| RMSE фільтра | 1.328 м, на 37% нижче сирого GNSS |
| RMSE у вікні відключення, фільтр / лише IMU | 6.942 м / 22.980 м |
| похибка на повторному захопленні (30.43 с), фільтр / лише IMU | 13.71 м / 32.09 м, відношення 2.3 |
